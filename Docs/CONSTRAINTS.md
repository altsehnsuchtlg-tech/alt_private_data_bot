# 总体约束

## 架构约束

- 项目继续保持分层架构：`bot` 负责 Telegram 交互，`managers` 负责业务编排，`services` 负责原子业务能力，`storage` 负责持久化，`infra` 负责外部基础设施适配。
- Handler 必须保持薄，只做参数解析、用户反馈、调用 manager，不直接堆业务逻辑。
- Manager 是用例编排层，负责串联 service、storage、infra 完成一个完整业务流程；manager 可以依赖 service、repository、queue、外部 client，但不应承载具体算法细节。
- Service 是业务能力层，负责可复用、可测试的原子业务能力；service 不负责跨组件流程编排，不应直接依赖 Telegram 类型，除非该服务的职责明确是 Telegram 相关能力。
- Worker 是后台消费入口，负责拉取消息、确认消息、日志和生命周期管理；具体业务处理必须转交 manager。
- 数据库读写应通过 repository 或明确的 storage 层封装，不在 handler 中直接写 SQL。
- 长耗时任务应避免长期阻塞 Telegram update handler，后续需要时再引入后台任务机制。
- 新增功能应优先复用现有配置、日志和 PostgreSQL，不引入重复基础设施。

## 数据约束

- PostgreSQL 用于长期业务数据、聊天记录、请求记录、错误日志等需要追踪的数据。
- 需要长期保存的数据必须有清晰的表结构、主键、时间字段和必要索引。
- 涉及状态流的数据应有明确状态字段，例如 `active`、`closed`、`processing`、`succeeded`、`failed`。
- 需要防重复处理的外部事件必须设计幂等键或唯一约束。
- 数据库 schema 变更应通过迁移脚本或迁移工具管理，不依赖手动临时 SQL。

## 配置约束

- 敏感信息只能通过环境变量或 `.env` 注入，不能写入代码、README 示例真实值或测试夹具。
- `.env.example` 只保留占位值和必要说明。
- 外部服务地址、模型名、超时时间、TTL、限制类参数应配置化。
- 默认配置应适合本地开发，Docker Compose 配置应适合容器网络。
- 新增配置项需要同步更新 `.env.example` 和相关文档。

## 错误处理与日志约束

- 用户可见错误应简短，不暴露异常堆栈、密钥、内部连接串或供应商响应细节。
- 需要排查的问题应写入结构化日志或数据库日志，保留事件名、错误类型、上下文 ID 和时间。
- 外部 API 调用失败必须被捕获并记录，不能让异常直接中断主循环。
- 不应在日志中无控制地写入大段用户输入或完整敏感 payload。

## 测试约束

- 新增核心业务逻辑必须配套测试，优先测试 manager、service 和 storage 层。
- Handler 测试应覆盖命令参数解析、用户反馈、错误路径和关键分支。
- 外部服务调用必须 mock，不在单元测试中真实请求 Telegram、OpenAI、Redis 或 PostgreSQL。
- 涉及数据库 schema、repository、事务的改动应有集成测试或迁移验证。
- 测试应可在干净环境重复运行，不依赖本地 `.env` 中的真实密钥。

## 安全与可靠性约束

- API key、bot token、数据库密码等敏感信息不得打印到日志。
- 外部输入需要限制长度，避免超大消息拖垮 handler、数据库或模型请求。
- 发送到外部模型或 API 的上下文应有上限，避免无限增长。
- 长回复需要考虑 Telegram 消息长度限制，发送失败要可追踪。
- 对可能产生费用的能力应预留限流、配额或权限控制位置。
- 同一用户或同一任务的并发处理需要考虑乱序、重复和竞态。

## 代码质量约束

- 遵循现有代码风格和目录组织，避免为单个功能引入不必要的大抽象。
- 新增注释应解释业务原因或复杂逻辑，不重复代码表面含义。
- 公共函数和跨层接口应有清晰类型标注。
- 不为无实际复用的逻辑提前抽象。
- 不在无关改动中重排格式、改行尾或重命名文件。

## 交付约束

- 每次功能更新应说明新增能力、配置变更、数据库变更和测试结果。
- 如果引入迁移，交付说明中必须包含迁移执行方式。
- 如果某项验证未能运行，需要明确说明原因和剩余风险。
